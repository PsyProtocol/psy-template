## 本轮改动

1. 回执读取按最多四个候选并行读取历史状态，完整等待该组结束，再按原事件顺序核对历史用户叶和 indexed content-hash 回执。跨轮询不缓存历史否定结果；缺回执保持未知。保留串行对照入口及全进程 RPC 并发上限。
2. 普通钱包增加单一身份的常驻进程。二进制、SDK manifest、配置、依赖清单及钱包文件绑定不变；私钥文件摘要只在内存检查，不归档。每项任务清空交易会话管理器，重新生成见证、nonce、签名和完整 UPS，仍核对代码、布局、费用、有效期和公开端点。
3. 普通钱包独立的公共依赖读取有界并行；当前用户叶与 nonce 状态并行读取，全部完成后才能通过。原串行模式用于对照。
4. 常驻进程一次只接收一个任务。ACK 不释放下一笔资金操作；必须在同一网络按原用户及 end leaf 找到确切收据。失败、断线及超时停止该进程，不自动重新证明或补发。
5. 同一钱包的并发对账共享一个正在执行的读取，并绑定原 gate 身份；迟到的 A 回执不能清除后续 B 交易的门闩。读取结束即清除 flight，不缓存完成的状态。
6. 单一 source-bound 候选的历史用户叶和收据并行读取，仍需两者完整匹配。
7. 新增普通钱包阶段计时，以及 ACK 到 indexed receipt / common checkpoint 的计时；公共电路启动与每笔证明分开记录。

## 验收及测量计划

在同一独立 QA Book 2497 / 金库 662720 上，依次运行两个新 epoch，使用相同两名用户、每侧 1 QA FT、同一费率、线程和调用规模。基线模块及二进制在运行前固定；候选使用常驻普通钱包和并行历史回执读取。只做普通新订单，不触碰旧代码或布局。

每轮必须包括：用户订单和转入、认证入队、集合封口、完整承诺与结算 UPS、普通钱包领取。保存交易原文、证明、状态端点、实际回执与资产快照；逐一完整验证证明及费用守恒后关闭。

报告分开给出：冷启动、暖态普通任务、完整证明、RPC / 确认观察、协议截止等待、领取、费用和采样内存。两个实际批次属于顺序配对，存在网络和运行顺序噪声，不能宣称稳态 TPS 或四市场普遍加速。必要时保留候选为显式实验配置，未测出收益的改动不升为默认。

### 优化版的原请求恢复

首两笔优化版订单已由原 native 客户端完成证明并广播。JS 在写性能 DTO 时误用仅支持整数的财务序列化器，导致父进程停止；原请求、证明、ACK 和 native 阶段计时均保留。现已按原 user/end-leaf/hash 精确确认两笔收据，未重新生成订单、证明或转账。

性能 DTO 改用 `saveObservation`，财务输入继续保留严格整数和 BigInt 约束，新增普通钱包入口集成回归。首两笔的外层总耗时缺失，最终报告置 null，不按文件时间补造；native 电路构建和任务阶段仍可查。重启后的 owner/buyer 首次 consent 仍是冷进程，不能计作暖态。后续 payout 和重复赞助任务才用于暖态对照。

顺序实测的 U124 起始余额不同：基线有 high-limb 进借位，下一轮未必相同。最终列出实际 slot 更新及 DA 费用差额，不把它当作缓存节费。初始资源观察器只捕获普通钱包进程，遗漏了封装后的 compact driver 摘要；本轮内存比较限于普通钱包 RSS，不补造完整 prover RSS。

## 保留的边界

- 此常驻入口是本机明确持有的 QA 普通钱包客户端能力，不等于浏览器扩展或所有 MCP 钱包已经迁移。
- 单进程门闩不代替跨机器账户协调。进程重启仍须从持久化请求和日志恢复原身份，不从余额猜测旧操作失败。
- 回执读取的历史并行不是交易、同池定价或证明的并行。
- 运行服务身份、升级授权、全市场公平性及认证未来随机源等外部边界仍按原 review 文档记录。
