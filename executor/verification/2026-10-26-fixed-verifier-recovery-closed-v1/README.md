## 真实故障与修复

1. 原基线在三笔普通 UPS 确认后读取检查点失败。新守卫只对明确耗尽传输重试的整组 heads 再读一次；不保留失败集合，也不重试金融广播。
2. 首次接纳在 SDK 会话开始阶段失败，完整 UPS 尚未生成。固定 SDK 的 `Request error` 文案原先未被已存在的窄范围恢复识别；新增同阶段、同端点、无证明材料的识别，并绑定内外两处 URL。错误身份、非传输错误、后续 VM 阶段及任何请求材料仍拒绝自动重启。
3. 封口完整证明已持久化，但 coordinator 提交前检查连接失败。保留首个未发送目录，重新检查原状态与窗口，复用**同一份完整证明和请求**，确认于 **383609**；没有重签或再次证明。原封口准备阶段为 89.087 秒，包含读取和递归，不能据此声称整个恢复快了同样秒数。
4. 精确复用守卫曾过宽，阻挡后续承诺的新证明，在签名/广播前安全停止。修复为只约束原操作，后续承诺与结算仍生成各自的新证明；已确认的承诺费用不再支付。
5. 第一次结算在 VM 证明过程中收到 RPC 空 JSON，原进程没有生成完整 UPS 或广播。单独核对固定 `serve-preflight` 证明进程、producer/策略/网络哈希、空请求目录、journal 及承诺后同一金库叶，再手动重建**原结算任务**。这不属于自动 pre-session 重试，不把局部 VM 工作冒充完整可复用证明，也不重做已确认承诺。
6. 修复保存快照 BigInt / 实时 Number 元数据比较，继续拒绝真实所有权、数量和 pending 变化。新增全部退出路径的子进程计时；写计时失败不会触发重复付款或掩盖原命令错误。历史缺失的外层计时不补造。

本轮三个 native 失败均明确在发送前；另有原公开检查点读取失败和上述应用守卫拒绝。完整原件保留。**122 项相关回归通过**，但结论依据实际证明、回执与资金账，而非测试数量。
